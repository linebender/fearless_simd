# Two additional compiler experiments

These are hand-written macro expansions, not finished procedural macros. Run on
x86-64 with stable Rust and Python 3:

```sh
python3 multiversion-research/alternatives/verify.py
```

Validated with rustc 1.97.1, `--edition=2024 -C opt-level=3`. Both executables check
results against a scalar/manual implementation; AVX2 execution is conditional on
CPU support. The script also compares generated AVX2 assembly against an
equivalent manually flattened loop using the parent project's `Assembly` checker:
branch label numbers are normalized and constant-pool references are replaced
with their actual contents before comparison.
Both comparisons pass, with no call instructions inside the specialized kernels.
This is an observed compiler result, not a language-level optimization guarantee.

## Callable marker: carry the protocol in the value's type

`callable_marker.rs` replaces a function item with a zero-sized `const mix: Mix`.
`Mix` implements `Deref<Target = fn(u32) -> u32>`, so ordinary `mix(x)` syntax still
works and invokes the public dispatch facade. Unlike a Rust function item, `Mix`
is nameable, so the macro can implement a specialization trait for it.

A generated call rewrite uses a zero-sized `Probe<F>` and autoref method
resolution to select between a specialized implementation and a fallback closure
containing the original call expression. The probe borrows the callable only to
infer its type; it retains no reference. Consequently, the fallback preserves
normal callable borrowing and consumption. The handwritten `call!(witness, f, x)`
expansion exposes the backend witness for inspection; a hypothetical attribute
would generate it. Its constructor is unsafe and its field private. Both adapter
traits are safe, so the generated rewrite does not enclose original argument or
callee expressions in an `unsafe` block. Compile-fail checks verify that unsafe
argument expressions and unsafe ordinary callees remain rejected.

The executable validates an annotated marker, a local alias of that marker, an
ordinary free function, an associated function, a capturing closure, repeated
`Fn` calls with a non-Copy capture, repeated `FnMut` calls, and a consuming `FnOnce`
call. The optimized marker kernel is emitted as an assembler alias of the manual
implementation on the tested compiler: `marker_process = manual_process`.

This avoids the companion-module protocol's need to decide whether a path is
importable. Important boundaries remain:

- The marker is callable through `Deref` but does **not** implement `Fn` traits.
  `iterator.map(mix)` and implicit coercion to a function pointer therefore stop
  working; an explicit closure or dereference can bridge that boundary.
- A `const` facade cannot express a generic function called as `mix::<T>(x)`.
- Probing a generic ordinary function without explicit type arguments can break
  inference: `call!(witness, std::convert::identity, 42u32)` produces E0282 because the
  probe and fallback instantiate the function separately. An explicitly typed
  path, or a locally bound function item used by both, avoids this particular issue.
- Calls through generic `F` inside a generic function resolve the fallback at
  generic-body type checking time unless the specialization bound is explicit.
- The proof rewrites only path callees. Arbitrary callee expressions with side
  effects must not be evaluated twice. Receiver-method calls are not specialized
  by this protocol, and the facade cannot replace inherent receiver methods.
- Only a single backend, call arity, and annotated signature are implemented.
  Backend protocol operations require a valid, privately constructed AVX2 witness.
- Arbitrary callbacks and macro-generated calls do not automatically propagate
  specialization; those uses need additional transformations or boundaries.

## Inline region: keep ordinary Rust name resolution

`inline_region.rs` models an annotation on a module/region whose public entry
points select a backend. Its ordinary raw implementation graph is marked
`#[inline(always)]`; an AVX2 entry point calls that raw graph with its CPU features
enabled. The original calls and signatures remain unchanged.

The raw graph includes a receiver method, an associated function, a helper call
generated by `macro_rules!`, and a local capturing closure. All inline into the
AVX2 entry point, producing exactly the same assembly as the manual loop. The
shared `Gain` type is defined only once.

This is a simpler boundary-based alternative. It depends on inlining, and the
raw methods are not independently dispatched public entry points. It does not
create a hidden generic `Simd` witness, handle non-inlineable calls or dynamic
callbacks, or solve module path/privacy preservation for a production macro.
